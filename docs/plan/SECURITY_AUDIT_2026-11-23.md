## 2. План работ

### Этап 1 — приложение — сделано 24.11.2026

Итог: п. 1 — база в выпуске только зашифрованная (`DbEncryption.requireCipher`,
экран «сборка не может зашифровать почту — установите заново», тест
`db_encryption_test`); п. 2 — 128 «атак» на очистку HTML (обычная, для окна
письма, для редактора) проходят, обходов не найдено
(`html_sanitizer_attacks_test`); п. 3 — разобраны все `exported`: главное окно
(«Поделиться» уже копирует файлы безопасно, + хранилище до разблокировки;
виджеты и ярлыки только открывают экраны, после PIN), окно настройки виджета
(теперь только свои виджеты), вход OAuth (PKCE S256 и проверка `state`),
службы синхронизации и администратора (защищены разрешениями системы);
п. 4 — вложения: все символы направления текста и невидимые, список
опасных расширений по Outlook, имена при сохранении (потоки NTFS,
зарезервированные имена Windows, точки в конце) — `attachment_safety_test`.

### Этап 1 — план (для истории)

1. **База только зашифрованная (п. 1).** В сборке release нет шифрования в
   библиотеке — не открывать базу без ключа: ошибка запуска с понятным экраном
   («сборка повреждена, переустановите»), запись в журнал. Без шифрования —
   только debug и тесты. Проверить, что старые незашифрованные базы
   (если такие были у ранних сборок) переводятся в шифрованные, а не
   теряются. Тест: библиотека без шифрования → в release — исключение, в
   debug — как сейчас.
2. **Очистка HTML (п. 10).** Набор тестов-«атак» на `html_sanitizer.dart` и
   `mail_body_processor.dart`: `<script>`, обработчики `on*`, `javascript:` и
   `vbscript:` в ссылках, SVG со скриптом, `data:` HTML, `srcset`,
   `<meta http-equiv=refresh>`, `<iframe>`, `<form>`, `<base>`, CSS
   `expression()`/`url(javascript:)`, вложенные и битые теги, кодировки
   (`&#x6A;avascript:`). Проверить, что внешние картинки не грузятся до
   разрешения (настройка «Загружать картинки сразу»), JS в WebView выключен.
3. **Экспортируемые компоненты и ссылки приложения (п. 9).** Разобрать каждый
   `exported="true"`: что принимает, кто может вызвать, проверка данных.
   Схемы `com.ogneliss.mail://` и `ogneliss-widget://`: что будет, если другое
   приложение зарегистрирует ту же схему (PKCE защищает код входа — проверить
   и все остальные пути). Убрать неиспользуемые разрешения после обновлений
   плагинов.
4. **Вложения (`attachment_safety.dart`).** Тесты: двойные расширения,
   `.lnk`/`.scr`/`.apk`/`.html` во вложении, подмена типа, имена с
   управляющими символами и `../`.

### Этап 2 — серверы (код — в сессии; на сервере применяет владелец)

5. **push-relay без ключа — не стартует (п. 7)**, как уже сделано в
   oauth-proxy. Режим «только внутренняя сеть» — явной переменной.
6. **Ограничение частоты в oauth-proxy (п. 5):** `/oauth/:provider/login`,
   `/callback`, `/token`, `/exchange` — лимит на адрес и на провайдера, пауза
   после неудачных `state` и обменов. Без новых пакетов (как лимит `/bimi`).
7. **Проверка подписи `id_token` (п. 8):** ключи провайдера (JWKS) с кэшем,
   `iss`, `aud`, `exp`. Встроенным `crypto` Node, без новых пакетов.
8. **`store.json` (п. 6):** зашифровать на диске тем же AES-256-GCM, что
   refresh-blob, либо вывести режим хранения на сервере из работы (нужно
   решение владельца, см. раздел 3).
9. **Токены в адресе возврата (п. 3):** после решения владельца — убрать
   ветку без PKCE (сервер отвечает «обновите приложение»).

### Этап 3 — по решению владельца

10. **Сертификаты пользователя (п. 2).** Вариант: строгий режим — для входа
    (OAuth, токены) и серверов с паролями сертификаты пользователя не
    доверяются, кроме явно разрешённых администратором (MDM) или принятых по
    отпечатку в приложении. По умолчанию — как сейчас (корпоративные ЦС
    должны работать). Ключ MDM `strict_tls`.
11. **Подтверждение подлинности приложения (п. 4)** — Play Integrity / App
    Attest. Только если будет реальная угроза (спам регистраций): сервисы
    бесплатные, но это новая зависимость и условия Google/Apple — сначала
    обсудить (правило CLAUDE.md о зависимостях).
12. **WebView на стабильную версию** — когда `flutter_inappwebview` выпустит
    стабильную 6.2 (бета взята ради исправлений; проверить при каждом
    обновлении зависимостей).

### Этап 4 — сопровождение (по мере работы, без спешки)

13. Разбить `app_database.dart` (таблицы, миграции, запросы по разделам —
    `part`-файлы или DAO) и вынести запуск из `main.dart` в отдельные службы.
    Только вместе с тестами миграций — риск потерять данные пользователей.
14. Пересмотреть `dependency_overrides`: что можно убрать.
15. Чек-лист безопасности для выпуска (в `docs/release/`): шифрование базы,
    разрешения манифеста, экспортируемые компоненты, сканер OSV, версии
    WebView и плагинов.

## 4. Что проверить дополнительно (в обзоре не было)

- Журнал (`AppLogger`) и файлы диагностики: нет ли в них токенов, паролей,
  полных адресов и текстов писем (маскирование уже есть — проверить все
  новые места за ноябрь: DAV, вложения, погода).
- Кэш вложений и временные файлы: удаляются ли при удалении ящика, не
  попадают ли в общие папки.
- Виджеты Android: в данных виджета нет текстов писем при включённом
  «скрытом» режиме (private).
- Уведомления на экране блокировки: видимость `private` везде, включая
  уведомления встреч и поручений.
- Удаление ящика: отзыв токенов OAuth у всех провайдеров, очистка
  `secure_storage`, кэшей DAV (`dav_res_*`, `dav_hidden_*`), погоды.
- Код при входе (PIN) и блокировка по бездействию: обход через виджет,
  уведомление, «Поделиться» в приложение.
- Сервер погоды и перевода: ограничение частоты, размер запросов.
