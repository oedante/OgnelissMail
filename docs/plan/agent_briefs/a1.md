# Task A1: mail view — dark mode without inversion, and clipping very long messages

Owner's request (31.10.2026), Ogneliss Mail 1.9.x. Main files: lib/features/mail/widgets/mail_html_view.dart (MailHtmlDocument.build, composeHtml with the `dark` inversion CSS around line 787, MailHtmlView widget, MailWebViewPool spare window), lib/features/mail/widgets/mail_native_body.dart (simple mails rendered natively), lib/features/mail/screens/mail_detail_screen.dart, lib/features/mail/providers/mail_open_cache.dart (documents prepared in advance), lib/features/archive/screens/archive_message_screen.dart (also uses MailHtmlView). Read them before changing anything; this code was tuned carefully (height measurement, UiZoomUndo on Android, spare WebView adoption, layout cache) — keep those mechanisms intact.

## 1. Dark theme: use the message's own dark version instead of inverting
Today in dark theme the whole document is inverted (`filter:invert(1) hue-rotate(180deg)`, images re-inverted). Many newsletters ship their own dark design via `@media (prefers-color-scheme: dark)` (and `<meta name="color-scheme" content="light dark">`, `:root{color-scheme:light dark}`).
- When dark theme is on and the message has a real dark design (a `prefers-color-scheme: dark` media block in its <style>), do NOT invert. Instead make that dark block apply: rewrite the CSS so `@media (prefers-color-scheme: dark){...}` rules apply unconditionally (also when the query is combined, e.g. `@media screen and (prefers-color-scheme: dark)`), and `prefers-color-scheme: light` blocks are dropped. Do it in Dart while building the document (the WebView engines differ: Android WebView with JS off, iOS WKWebView, Windows WebView2 — do not rely on the engine's own media matching). Set the page background to the app page colour only if the message does not set its own.
- Messages without a dark design keep the current inversion.
- Add a per-message toggle "Исходные цвета" (show the message exactly as designed, light, no inversion) in the message's ⋮/More menu in mail_detail_screen (and archive message screen if simple). Remember the choice per message for the session (in memory is fine; per sender persistent is optional).
- Native body (mail_native_body.dart): check how it handles dark mode; keep it consistent (it renders simple mails, no CSS media queries — probably nothing to do; confirm).
- Cache keys: the document/HTML memo keys, MailWebViewPool.take matching and mail_open_cache must include the new mode so a light document is never reused for dark or vice versa.

## 2. Clip very long messages with "Показать письмо целиком"
Like Gmail's "[Сообщение обрезано]" / K-9: huge messages (giant newsletters, long threads with quoted history, logs) make the WebView very tall and memory-heavy (we just added recovery from WebView renderer crashes).
- In MailHtmlDocument.build (or right after), when the message body is very large (choose a sensible threshold, e.g. ~150 KB of HTML not counting inline image data URIs, or a node-count/text-length based one — justify in a comment), cut the DOM at a block boundary so the kept part is a well-formed prefix, and mark the document as clipped (expose e.g. `bool clipped` on MailHtmlDocument).
- The detail screen shows a button "Показать письмо целиком" under the message when clipped; tapping it re-renders the full document (same widget, new document; height must be re-measured correctly — the WebView document is never shorter than the window, so make sure the height can only grow here, which is fine).
- Same for the native body path if it can receive huge content (check how long simple mails go there) and for plain-text mails (mail_detail_screen renders plain text with LinkifiedText — clip very long plain text too, with the same button).
- Printing / forwarding / replying must still use the full message (clip only the display).
- l10n keys for the button and the toggle in all 27 languages.
