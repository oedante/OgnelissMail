# Анализ: «код есть, но не вызывается»

Систематическая проверка после того, как за одну сессию нашлось **девять**
случаев подряд. Закономерность оказалась не случайной.

## Метод

Скрипт собрал все публичные методы в `lib/services/**` и `lib/data/**` и
проверил, вызывает ли их хоть кто-то **за пределами своего файла**. Переопределения
(`build`, `dispose`, `initState`, `toJson`…) исключены.

## Результат

| | |
|---|---|
| Файлов проанализировано | 223 |
| Публичных методов в services/data | 371 |
| **Не вызываются извне** | **114 (31%)** |
| Сервисов без единой ссылки | **15 (~1 900 строк)** |

Треть публичного API сервисов недостижима из приложения.

## Но цифра требует разбора

Слепо «31% мёртвого кода» — неверный вывод. Ручная проверка показала **три
разных класса**, и лечатся они по-разному.

### Класс А. Дубли-сироты — функция РАБОТАЕТ, но через другой код

* **`snooze_service`** (`snoozeEmail`, `scheduleEmail`, `getSnoozeTime`) —
  не вызывается. Но снуз **работает**: он реализован в
  `email_actions_service.scheduleEmailReminder` + поле `emails.remindAt`, UI —
  в карточке письма. То есть это **параллельная реализация того же самого**,
  оставшаяся не у дел.
* Аналогично часть методов `email_export_service` дублирует `eml_builder`.

**Лечение:** удалить дубль. Опасность не в «мёртвом коде», а в том, что
следующий разработчик доработает **не ту** реализацию.

### Класс Б. Настоящие пробелы — функции НЕТ

* **`draft_autosave_service`** (`startAutosave`, `forceSave`, `updateDraft`…) —
  не вызывается. Черновик сохраняется только по кнопке «Сохранить черновик».
  **Автосохранения нет**: свернул приложение на полуслове — текст потерян.
* **`conflict_resolver`** (`detectConflicts`, `resolveConflict`, `setStrategy`…) —
  не вызывается **нигде**, UI отсутствует. Конфликты синхронизации (правка на
  двух устройствах) не обнаруживаются и не разрешаются — тихо побеждает
  последняя запись.
* **`auto_responder_service`** (6 методов настройки) — не вызывается, UI нет.
  При этом OOF на сервере работает: `ews.getOofSettings/setOofSettings`
  доступны через фасад. То есть **серверная часть есть, интерфейса нет**.
* **`smart_compose_service`** (`getSuggestions`, `learnFromSentEmail`) —
  подсказки при наборе не показываются.
* **`local_gpt_service`**: `predictAction`, `predictTag`, `predictTemplate`,
  `recordAction` — персонализация ИИ не обучается и не применяется.

**Лечение:** дописать вызов из UI. Сам механизм уже готов и оплачен временем.

### Класс В. Ложные срабатывания

* Методы, вызываемые только внутри своего файла или через фасад
  (`activesync_service.provision` зовётся из транспорта того же слоя).
* `ews.sendAs`, `downloadAttachmentToFile` — используются в редких ветках.
* Провайдеры и точки расширения, вызов которых появится позже.

**Лечение:** не требуется, но стоит пометить `@visibleForTesting` или
приватизировать, чтобы не искажать картину.


### Класс Г. Фиктивные реализации — код ВЫПОЛНЯЕТСЯ и не делает ничего

Найдено при разборе класса А и оказалось опаснее всего остального.

**Два сервиса для badge на иконке — и оба фикция:**

* `unread_badge_service` (25 строк) — зовёт `MethodChannel('ogneliss/badge')`.
  Нативной реализации канала **нет ни на одной платформе**. Сервис ловит
  `MissingPluginException` и **молча игнорирует** — то есть спроектирован так,
  что отсутствие работы неотличимо от работы.
* `badge_service` (57 строк) — честно считает непрочитанные по всем аккаунтам,
  затем: `final iosPlugin = _notifications.resolvePlatformSpecificImplementation<…>()`
  — переменная **не используется**; далее `AppLogger.debug('Badge updated: $total')`.
  `clearBadge()` — только `AppLogger.debug('Badge cleared')`.

**Почему это хуже несвязанного кода.** Несвязанный код виден: его никто не
зовёт. Фиктивный — зовётся, пишет в лог «Badge updated: 5», не падает. Проверка
по логам показывает успех. Разработчик считает пункт закрытым; пользователь
badge не видит и не понимает почему.

**Признаки, по которым узнаётся:**
* переменная получена и не использована;
* тело метода — только логирование;
* `catch` без действия там, где отсутствие поддержки нормально;
* комментарий вида «на iOS обновляется автоматически» вместо кода.

**Лечение:** удалить. Оба сервиса удалены; badge остаётся ⬜ в Этапе 9 с честной
пометкой, что нужна настоящая реализация (нативный код или пакет уровня
`app_badge_plus`; `badges: ^3.1.2` в pubspec — это виджет ВНУТРИ приложения, к
иконке отношения не имеет).

## Почему так вышло

Код писался **слоями снизу вверх**: протокол → сервис → фасад → UI. Нижние слои
доводились до конца, верхний — вызов из интерфейса — регулярно нет. Снаружи всё
выглядит готовым: файл на месте, методы полные, тесты бы прошли. Не хватает
одной строки в том месте, куда никто не смотрел.

Отсюда практический вывод: **список ⬜ в дорожной карте не отражает реальность**.
Часть пунктов давно сделана (группировка уведомлений), часть готова на 90% и ждёт
одной строки (push), часть помечена ✅, хотя не работает (`EmailFetchMode`).

## Что делать

1. **Проверять сверху вниз, а не снизу вверх.** Вопрос не «написан ли метод»,
   а «дойдёт ли до него нажатие кнопки».
2. **Прогонять этот скрипт регулярно** (`/tmp/find_unwired.py`, вынести в
   `scripts/`). 114 → цель приблизить к числу осознанных исключений.
3. **Приоритет — класс Б:** автосохранение черновиков, автоответчик (UI),
   разрешение конфликтов, персонализация ИИ.
4. **Класс А удалить** до того, как кто-то доработает не ту реализацию.
