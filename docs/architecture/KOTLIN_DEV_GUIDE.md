# Ogneliss на Kotlin: инструкция для начала разработки

Документ для переноса корпоративного почтового клиента с Flutter на нативный
Android. Основан на существующей реализации: 65 000 строк, 54 экрана, 17 таблиц,
три почтовых протокола.

**Главная мысль.** Самое ценное здесь — не код, а знание крайних случаев:
что ломается при обрыве связи, как ведёт себя русский Outlook, почему письмо
уходит без вложений. Код перепишется за месяцы, эти знания добывались
экспериментом. Раздел 9 — самый важный в документе.

## 2. Структура проекта

Модульная сборка. Ключевое решение: **транспорты отделены от UI** — так их можно
тестировать без Android и переиспользовать.

```
app/                        Compose-экраны, ViewModel, DI, навигация
core/
  core-model/               Модели данных (чистый Kotlin, без Android)
  core-db/                  Room: сущности, DAO, миграции
  core-crypto/              Хранение секретов, TLS-пиннинг
mail-engine/                ЧИСТЫЙ Kotlin, без Android:
  transport-eas/            ActiveSync + WBXML-кодек
  transport-ews/            Exchange Web Services (SOAP)
  transport-imap/           IMAP/SMTP
  autodiscover/             Определение сервера
feature/                    По одному модулю на раздел
  feature-mail/  feature-calendar/  feature-contacts/
  feature-tasks/ feature-notes/     feature-settings/
```

Почему `mail-engine` без Android: его код запускается в обычных JVM-тестах, без
эмулятора. Для WBXML это критично — иначе каждая проверка занимает минуты.

## 3. База данных

**17 таблиц**, схема в текущей версии — 14 (14 миграций):

| Таблица | Назначение |
|---|---|
| `accounts` | Учётные записи, включая общие/делегированные ящики |
| `emails` | Письма: тело, вложения (JSON), флаги, `remindAt`, `followUpAt` |
| `folders` | Папки с типом (inbox/sent/junk/archive) — **тип, а не имя** |
| `contacts`, `calendar_events`, `tasks`, `notes` | PIM |
| `sync_queue` | Офлайн-очередь операций |
| `audit_log`, `signatures` | Журнал, подписи |
| `assignments` + 6 сателлитов | Поручения и согласования |

**Что перенести обязательно:**
- Индексы. Их много и они не косметика: `idx_emails_conversation` (цепочки),
  `idx_emails_followup` (частичный, `WHERE follow_up_at IS NOT NULL`),
  индексы по `account_id + folder_id + received_at` для пагинации.
- FTS5 для полнотекстового поиска писем.
- WAL-режим и `foreign_keys = ON`.

**Миграции.** Room требует явных `Migration(N, N+1)`. Начинать с версии 1 —
существующие базы Flutter-версии всё равно не откроются (разный формат имён
таблиц). Это означает, что **при переходе пользователи потеряют локальный кэш**
и синхронизируют почту заново. Об этом нужно предупредить: на большом ящике
первая синхронизация занимает минуты.

## 4. Транспорты — самая трудоёмкая часть

### 4.1 ActiveSync (EAS) — начинать с него

Самый сложный и самый важный: именно от него зависит, нужен ли вообще переход.

**WBXML-кодек** (~600 строк) — бинарный формат вместо XML.

⚠ **Уточнение:** писать с нуля не нужно. В AOSP есть реализация на Java под
Apache 2.0 (`Parser.java`, `Tags.java`) — см.
[`KOTLIN_LIBRARIES.md`](KOTLIN_LIBRARIES.md), раздел 3. Там же про
лицензирование EAS, которое стоит выяснить до начала работ.

Что должен уметь кодек:
- таблицы кодов страниц (AirSync, Email, Calendar, Contacts, Provision…);
- переключение страниц (`SWITCH_PAGE`);
- строковые таблицы, инлайн-строки, opaque-данные;
- кодирование и декодирование симметрично.

**Порядок работ:**
1. Кодек с юнит-тестами на готовых образцах (снять из текущей реализации).
2. `Provision` — PolicyKey, политики. Без него сервер откажет.
3. `FolderSync` — дерево папок.
4. `Sync` — письма, дельта-синхронизация по `SyncKey`.
5. `Ping` — push-уведомления (долгий запрос, держать в WorkManager).
6. `SendMail`, `ItemOperations` (вложения).

**Подводные камни** (проверено на боевом Exchange):
- Версию протокола согласовывать через `OPTIONS`: сервер отдаёт поддерживаемые
  в заголовке. Жёстко задавать 14.1 нельзя — 2016/2019 отвечают иначе.
- `PolicyKey` меняется; при `HTTP 449` — перезапросить и повторить.
- `MaxAttachmentSize` приходит в Provision. Читать заранее, иначе отправка
  крупного файла упадёт после полной загрузки на сервер.
- Вложения при отправке — `multipart/mixed`, base64 по 76 символов (RFC 2045),
  имена по RFC 2047.

### 4.2 EWS (Exchange Web Services)

SOAP/XML — проще EAS. OkHttp + `XmlPullParser`.

Операции: `FindFolder`, `FindItem`, `GetItem`, `CreateItem`, `UpdateItem`,
`MoveItem`, `DeleteItem`, `SyncFolderItems`, `SendItem`, `Forward`.

**Ключевое для общих ящиков:** чтобы обратиться к чужому ящику, в
`DistinguishedFolderId` вкладывается `<t:Mailbox><t:EmailAddress>`. Без этого
запрос уйдёт в собственный ящик пользователя. Касается и чтения, и папки
«Отправленные» при отправке.

Аутентификация: Basic и **NTLM** (для локального Exchange за периметром).
NTLM в OkHttp — через `Authenticator`; готовой реализации в стандартной
библиотеке нет.

### 4.3 IMAP/SMTP

**Jakarta Mail 2.x** работает на Android напрямую, есть IDLE для push и
встроенный OAuth2 (SASL на Android не поддерживается — см.
[`KOTLIN_LIBRARIES.md`](KOTLIN_LIBRARIES.md), раздел 1).

Важно: IMAP-сессия одна на соединение, и `SELECT` переключает текущую папку.
Параллельные запросы к разным папкам **обязаны** идти через мьютекс на аккаунт,
иначе один запрос уводит папку у другого.

### 4.4 Autodiscover

POX-запрос к `autodiscover.<домен>/Autodiscover/Autodiscover.xml`, затем к
`<домен>/…`. Возвращает и `EwsUrl`, и `ASUrl` — **это разные вещи**, путать
нельзя: SOAP-запросы к адресу ActiveSync падают.

**Гибридный режим:** если подключились по EAS, а Autodiscover отдал `EwsUrl` —
сохранить его. EAS даёт push и экономию батареи, EWS — автоответы, занятость
коллег, категории, серверные правила, отзыв письма. Так работают Nine и
OfficeMail.

## 5. Экраны (54)

| Раздел | Экранов | Основные |
|---|---:|---|
| Настройки | 30 | Аккаунты, почта, свайпы, уведомления, безопасность, синхронизация, журнал |
| Почта | 4 | Список, письмо, поиск, хаб вложений |
| Авторизация | 4 | Вход, ручная настройка, OAuth, общий ящик |
| Дашборд | 3 | Сводка, «Мои сроки», отчёт по переписке |
| Поручения | 3 | Список, детали, создание |
| Календарь, контакты, заметки | 6 | |
| Задачи, хранилище, подписки | 3 | |
| Написание письма | 1 | Самый сложный экран |

**Порядок реализации.** Не по разделам, а по сценарию «первый запуск → чтение →
ответ»:

1. Вход (ручная настройка, без OAuth) → список писем → просмотр письма.
2. Написание и отправка.
3. Папки, поиск, свайпы.
4. Календарь → контакты → задачи.
5. Настройки (по мере надобности, а не все 30 сразу).
6. Дашборд, поручения, заметки.

Так рабочий продукт появляется на 2–3 месяце, а не в конце.

## 6. Компоненты, требующие отдельного внимания

**Просмотр HTML-письма.** Аналога `flutter_html` нет — только WebView. Настройки
обязательны:
- `javaScriptEnabled = false` — письмо не должно выполнять скрипты;
- блокировка внешних ресурсов до явного согласия (трекинговые пиксели);
- `setSupportZoom(true)`, `useWideViewPort` — иначе таблицы не читаются.

Санитизация HTML **до** показа: вырезать `<script>`, `<iframe>`, обработчики
`on*`. Библиотека **Jsoup** с белым списком тегов.

**Редактор письма.** Готового нет. Варианты: WebView с `contenteditable` и своей
панелью инструментов (как сейчас) либо сторонний редактор. Обязательна очистка
вставки из Word/Excel: условные комментарии, `mso-*` стили, `MsoNormal`,
`<o:p>` — иначе таблица из Excel даёт письмо в сотни килобайт.

**Сворачивание цитаты.** Разбор по маркерам. Для русского Outlook нужны:
«Иванов И.И. **пишет:**», «15.01.2026 Иванов **написал(а):**», блок
«**Отправлено:**», `<hr>` перед «От:», строка подчёркиваний. Без них цитата не
свернётся, и каждое письмо в цепочке выглядит простынёй.

**Уведомления.** Каналы: письма, напоминания, синхронизация. Группировка по
`accountId`. В заголовке — отправитель, а при нескольких ящиках ещё и адрес
ящика. Для общего ящика пометка обязательна и идёт первой.

**Переносится почти дословно** (логика, не синтаксис):
- таблицы кодов WBXML;

- регулярные выражения: извлечение сроков, разбор цитат, определение

**Не переносится:** весь UI, работа с состоянием, навигация, DI.

## 9. Крайние случаи — самое ценное

Список добыт экспериментом. Повторно он обойдётся дороже, чем весь остальной
перенос.

**Отправка и очередь**
- Между отправкой на сервер и удалением записи из очереди есть окно: если
  приложение убьют в этот момент, письмо уйдёт **дважды**. Устраняется только
  дедупликацией по `Message-ID` на сервере. Выбор в пользу дубликата, а не
  потери — осознанный: в деловой переписке пропавшее письмо хуже.
- Вложения в очереди хранить **как данные, а не путь к файлу**: временный
  каталог ОС очищается, и письмо уйдёт без файла.
- Ограничить суммарный размер очереди (200 МБ): base64 раздувает вложения на
  треть, и пять писем по 25 МБ дают проблемы с памятью.
- Дедупликация операций: три переключения флага подряд — одна запись, иначе при
  восстановлении связи на сервер уходит череда повторов.
- При исчерпании попыток письмо **не удалять молча** — помечать и уведомлять.

**Пересылка**
- Вложения оригинала могут быть не скачаны. Тогда пересылку делать **на
  сервере** (EWS `ForwardItem`) — он приложит файлы сам. Если сервер не может,
  скачать заранее, иначе письмо уйдёт без вложений и человек не узнает.

**Аутентификация**
- Отличать отказ в аутентификации (401/403, `AUTHENTICATIONFAILED`, `logon
  failure`) от сетевого сбоя (таймаут, TLS, 503). Иначе при нестабильной связи
  аккаунт будет помечен проблемным.
- При смене пароля продолжать попытки опасно: на многих серверах несколько
  неудачных входов подряд блокируют учётную запись.
- OAuth-токен обновлять **до** синхронизации, а не после ошибки 401.

**Данные**
- Папки искать **по типу** (`FolderType.junk`), а не по имени или ID: у EWS это
  `junkemail`, у IMAP «Спам» или «Junk».
- `firstWhere` без запасного значения роняет операцию, если аккаунт удалён, а
  уведомление или запись очереди его пережили.
- Контакты и календарь фильтровать по аккаунту: иначе при нескольких ящиках
  адресные книги смешиваются.

**Интерфейс**
- Общий ящик выделять **везде** — письма, календарь, контакты, задачи, выбор
  отправителя, уведомления. Ответить от чужого имени слишком легко.
- Массовые действия размещать **внизу** экрана: до верхней панели не дотянуться
  одной рукой.
- Скрывать панели при прокрутке вниз с порогом ~12 px, иначе они мигают от
  дрожания пальца. На планшете не скрывать.

**Локализация**
- `\b` в регулярных выражениях работает по ASCII: с кириллицей граница слова не
  определяется. В Kotlin то же самое — использовать явную проверку начала слова.

## 10. Что сделать иначе

Выводы из текущей реализации:

1. **Репозитории с самого начала.** Сейчас 13 экранов ходят в БД напрямую —
   схему не поменять, не трогая UI.
2. **Экраны не больше 400 строк.** Здесь есть файлы по 2000: правка одной
   функции задевает соседние, тестировать невозможно.
3. **Тесты на транспорты сразу, а не потом.** WBXML, очередь, разбор ответов —
   чистые функции, тестируются легко. Сейчас они не покрыты, хотя ломаются
   больнее всего.
4. **CI с первого дня:** `ktlint` + `detekt` + тесты на каждый коммит.

## 11. Первые шаги

1. Создать проект: Android Studio → Empty Compose Activity, minSdk 26.
2. Настроить модули по разделу 2 (можно начать с `app` + `mail-engine`).
3. Room: сущности `accounts`, `emails`, `folders` + первая миграция.
4. **WBXML-кодек с тестами** — до всего остального UI.
5. Проверить `Provision` и `FolderSync` на боевом Exchange.

Если шаг 5 проходит — переход имеет смысл. Если нет — стоит вернуться к вопросу
до того, как написан UI.
