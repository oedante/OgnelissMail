## 2. Мешающие друг другу операции (гонки)

### 2.1 ❗ Гонка SELECT/FETCH в IMAP — **найдена и исправлена**

IMAP имеет состояние: `SELECT папка` → `FETCH`. Клиент у аккаунта **один общий**.
Внутренняя очередь `enough_mail` сериализует отдельные команды, но не группирует
их в транзакцию. Две параллельные операции чередовались так:

```
SELECT «Отправленные» · SELECT «Входящие» · FETCH · FETCH
                                             ↑ читает ЧУЖУЮ папку
```

**Последствие:** письма сохранялись не в ту папку. Сценарий не редкий: фоновый
синк идёт по одной папке, пользователь тянет вниз в другой. Существующий guard
`_foldersSyncing` защищал только от повтора *одной и той же* папки.

**Исправлено:** мьютекс на аккаунт (`_withAccountLock`) — пара «выбрать папку +
работа с ней» выполняется целиком. Обёрнуто 9 методов: `getEmails`,
`getEmailDetail`, `fetchAttachment`, `markAsRead`, `flagEmail`, `moveEmail`,
`deleteEmail`, `getServerQuota`, `getFolders`. `sendEmail` не обёрнут — он только
SMTP.

### 2.2 ⚠️ IDLE требует ОТДЕЛЬНОГО соединения

`startIdle` делает `SELECT` и держит соединение постоянно. Под общим мьютексом он
заблокировал бы всё остальное навсегда, а без мьютекса — конфликтует с обычными
операциями. Правильное решение — **отдельный IMAP-клиент под IDLE** (так делают
все зрелые клиенты). Сейчас IDLE никем не вызывается, поэтому вреда нет.

### 2.3 ✅ Что проверено и конфликтов не даёт

* `syncAccount` обходит папки **последовательно** (`await` в цикле).
* Drift сериализует запись; `.watch()`-потоки переизлучаются после коммита.
* Офлайн-очередь (`sendOrQueue`) — единая точка исходящих.
* Уведомления планируются в ОС, от сети не зависят.

## 3. Чего не хватает для полноценного клиента

### Приоритет 1 — ядро (заметно сразу)

| Что | Почему важно | Объём |
|---|---|---|
| **IMAP IDLE подключить** | Push вместо опроса по таймеру. Реализовано, но никто не вызывает — личные ящики узнают о письме с задержкой до интервала синка. Нужен отдельный клиент под IDLE. | средний |
| **Превью вложений** | Открыть PDF/картинку/документ, не выходя из письма — один из самых частых запросов в магазинах. | средний |
| **POP3 или удалить поля** | Сейчас схема обещает то, чего нет. | средний / малый |

### Приоритет 2 — ожидаемое пользователями

| Что | Комментарий |
|---|---|
| **Резервная копия и восстановление** | Экспорт аккаунтов/правил/подписей/шаблонов. Для корпоратива — перенос на новое устройство. |
| **Виджет на рабочий стол** (Android) | Частый запрос: непрочитанные без открытия приложения. |
| **Уведомления о прочтении для IMAP** | Есть только для EWS (`sendReadReceipt`). В IMAP — заголовок `Disposition-Notification-To`. |
| **Группировка уведомлений** | Сейчас каждое письмо — отдельное уведомление; шторка забивается. |

### Приоритет 3 — на развитие

* **PGP** (S/MIME уже есть — `smime_service.dart`).
* **Push для Exchange** (EAS Ping) — аналог IDLE.
* **Лицензирование** — требует своего сервера (см. ниже).

## 4. Лицензирование — почему это «на развитие»

Оценка по факту: полноценное лицензирование требует **серверной части** —
выпуск, продление, отзыв, проверка, привязка к устройству/пользователю. Это
отдельный сервис с базой, а не флаг в приложении: любую локальную проверку
обходят правкой APK.

Инфраструктура для этого частично есть: VPS, домен, Docker, Nginx Proxy Manager,
и уже работающий OAuth-прокси — образец того же класса (stateless, ключ на
сервере, приложение секретов не знает).

**Разумная последовательность (когда дойдут руки):**
1. Офлайн-лицензии с подписью Ed25519: сервер выпускает файл-ключ, приложение
   проверяет **публичным** ключом. Сервер не нужен в рантайме — только для выпуска.
2. Онлайн-активация: привязка к устройству, отзыв, счётчик мест.
3. Панель управления лицензиями.

Пункт 1 закрывает 80% задачи малой кровью и не требует постоянного сервера.
**Сейчас не делаем** — приложение нужно тестировать целиком, а лицензия только
мешала бы.

## 5. Итог

Ядро для корпоративного клиента **собрано**: Exchange (EAS+EWS), IMAP/SMTP,
календарь, контакты, задачи, заметки, правила, подписи, S/MIME, офлайн-очередь,
шифрование БД, remote wipe, аудит.

Главный риск был **не в отсутствии функций, а в гонке IMAP** — она портила
данные молча. Исправлено.

Ближайшее по ценности: **IDLE (push)** и **превью вложений** — обе заметны
пользователю сразу.
