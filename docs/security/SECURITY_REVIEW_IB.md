# Mail — карточка для согласования в ИБ

Документ описывает обрабатываемые данные, технологический стек, сетевые
взаимодействия и защитные механизмы клиента **Mail** для предварительной
оценки службой информационной безопасности.

Статусы: ✅ реализовано · 🟡 частично / в доработке · 🔧 требует решения/согласования ИБ.

---

## 1. Назначение и архитектурная модель

Кроссплатформенный корпоративный почтовый клиент (почта, календарь, контакты,
задачи, заметки). Архитектура — **«толстый клиент»**: приложение подключается
**напрямую** к корпоративному Exchange и к выбранным пользователем почтовым
сервисам. **Серверов или облаков разработчика в контуре обработки нет** — данные
не проходят через промежуточные сервисы.

- Платформы: Windows, macOS, Linux, Android, iOS, Web.
- Развёртывание: внутренняя дистрибуция; публикация в магазинах — на этапе плана.

## 3. Обрабатываемые данные

| Категория | Состав | Где |
|---|---|---|
| Учётные данные | Логин, пароль (для Exchange Basic / IMAP по паролю) | Secure storage ОС |
| Токены OAuth | access/refresh-token (Google/Yandex/Mail.ru) | Secure storage ОС |
| Содержимое почты | Письма, заголовки, тела, вложения | Локальная БД + файловый кэш вложений |
| ПДн и корп. данные | Контакты (ФИО, email, телефоны), события календаря, задачи, заметки | Локальная БД |
| Метаданные синхронизации | Sync-ключи (EAS/EWS) | `shared_preferences` |
| Журнал аудита | Входы и ключевые операции | Локальная БД |

Данные хранятся **локально на устройстве пользователя**. Передача — только между
устройством и почтовым сервером (см. §5).

## 4. Хранение данных (at-rest)

- ✅ Секреты (пароли, токены) — в защищённом хранилище ОС (`flutter_secure_storage`).
- ✅ Локальная БД зашифрована на Android, iOS, Windows, macOS и Linux:
  SQLite3 Multiple Ciphers подключает build-хук пакета `sqlite3`, ключ базы —
  в защищённом хранилище ОС. Если хранилище ключей не отдало ключ, база не
  открывается (не пересоздаётся пустой и не открывается без шифрования).
- Кэш вложений — во внутреннем каталоге приложения (sandbox ОС).

## 5. Сетевые взаимодействия

Исходящие соединения инициируются только клиентом; входящих слушающих портов нет
(кроме временного loopback `127.0.0.1` на desktop при OAuth — см. §6).

| Назначение | Хост (пример) | Порт | Протокол |
|---|---|---|---|
| Exchange (рабочий) | `mail.example.com` | 443 | HTTPS (EWS + EAS) |
| Exchange autodiscover | `*.example.com` | 443 | HTTPS |
| IMAP / SMTP (внешние) | сервер провайдера | 993 / 465–587 | TLS |
| OAuth (по выбору пользователя) | Google / Yandex / Mail.ru | 443 | HTTPS |

- Весь трафик — поверх TLS. Содержимое переписки во внешние сервисы (кроме
  собственно почтового сервера аккаунта) **не передаётся**.
- 🔧 **Замечание для ИБ:** корпоративное правило периметра блокирует отправку на
  публичные адреса (наблюдалось `550 TRANSPORT.RULES.RejectMessage`) — учитывается.

## 6. Проверка TLS-сертификатов

Реализованы два механизма (важно для оценки ИБ):

1. 🟡 **Доверие внутреннему УЦ.** Сертификат, не прошедший системную проверку,
   оценивает `CertificatePinningService` (все HTTP-клиенты приложения, включая
   движок EAS): принят пользователем по отпечатку SHA-256 для этого хоста;
   выпущен ЦС Минцифры, включённым для ящика; хост входит в список «доверенных
   доменов». Список доменов по умолчанию пуст; домен из списка принимает
   **любой** сертификат. 🔧 **Вопрос ИБ:** установка корня внутреннего УЦ в
   доверенные ОС (MDM) или закрепление отпечатков (п. 2) — вместо «доверенных
   доменов». В выпускаемой сборке режим «принимать всё» недоступен.
2. ✅ **Certificate pinning (настраиваемый).** Сервис `certificate_pinning_service`
   с режимами `off / trustStore / pinned`; для заданных доменов — строгая сверка
   **SHA-256-отпечатков** (base64 от DER). Готов к включению по отпечаткам,
   предоставленным ИБ.

## 7. Аутентификация

- Exchange: Basic (`ДОМЕН\<логин>` + пароль) поверх TLS и/или ActiveSync; пароль —
  только в secure storage, передаётся по TLS. 🔧 ИБ может предписать современную
  аутентификацию (OAuth/Modern Auth) при её доступности на сервере.
- Внешние провайдеры: **OAuth 2.0 + PKCE (S256)**, без хранения клиентских
  секретов в приложении (публичный клиент).
- ✅ Защита от повторного добавления одного и того же аккаунта.

## 9. Телеметрия и сторонние сервисы

- ✅ **Аналитики/телеметрии нет**: в зависимостях отсутствуют Firebase, Sentry,
  Crashlytics, аналитические SDK. Данные пользователя никуда не выгружаются.
- Локальный ИИ (категории/теги/настроение/быстрые ответы) — **полностью на
  устройстве**, на правилах; обращений к внешним ИИ-сервисам нет.
- Логи — локальные (`logging`), уровень настраивается; без отправки вовне.

## 12. Открытые вопросы для согласования с ИБ

1. Способ доверия внутреннему УЦ: установка корня в ОС/MDM **или** строгий pinning
   по SHA-256 (предоставить отпечатки) — вместо «доверенных доменов».
2. ~~Шифрование локальной БД на всех платформах~~ — решено: SQLite3 Multiple
   Ciphers на всех нативных платформах (§4).
3. Допустимость Basic-аутентификации для Exchange или требование Modern Auth.
4. Объём удалённой очистки по политике EAS и хранения данных на устройстве.
5. Включение защиты от скриншотов и иных hardening-настроек.
6. Политика логирования и срок хранения локальных журналов/аудита.
