## 1. Bounce / NDR parsing
- Recognise delivery status notifications arriving in any synced folder: `multipart/report; report-type=delivery-status` (RFC 3464) with a message/delivery-status part, and common non-standard bounces (Postfix/Exim/Exchange NDR texts "Undelivered Mail Returned to Sender", "Mail delivery failed", "Delivery Status Notification (Failure)", "Недоставленное сообщение", Yandex/Mail.ru formats) — be conservative.
- Extract: original Message-ID (from the message/rfc822 or text/rfc822-headers part, or In-Reply-To/References), failed recipients, action (failed/delayed/delivered/relayed), status code (5.1.1 …) and diagnostic text.
- Link to the original sent message by Message-ID (internetMessageId in the emails table) and store per-recipient delivery status.
- UI: on the sent message (message screen header area) a clear line: "Не доставлено: user@x — адрес не существует (5.1.1)" with a human explanation for common codes (mailbox full, no such user, blocked as spam, domain not found, delayed — will retry), and actions "Отправить снова" / "Изменить адрес". In the list (Sent folder / conversation) a small red icon on undelivered messages. The bounce message itself stays in the inbox (do not delete user mail) but may be shown with a "Отчёт о доставке" chip linking to the original.
- Notification: a bounce for a message sent in the last few days triggers a clear notification "Письмо не доставлено" instead of the generic new-mail one (respect quiet hours).

## 2. DSN request (RFC 3461)
- If the SMTP server advertises DSN in EHLO: on MAIL FROM add `RET=HDRS ENVID=<id>` and on RCPT TO `NOTIFY=FAILURE,DELAY` by default (this is what servers do anyway, but it gives reliable machine-readable reports with ENVID). Optional per-message "Запросить подтверждение доставки" in compose options → `NOTIFY=SUCCESS,FAILURE,DELAY`; success reports then mark recipients as "Доставлено на сервер получателя" (explain in UI that it is not a read receipt).
- enough_mail SmtpClient: check whether MAIL FROM/RCPT TO parameters can be passed without modifying enough_mail (it is MPL-2.0 — do not edit its files; subclassing like TolerantSmtpClient is fine). If impossible, implement only bounce parsing and report.
