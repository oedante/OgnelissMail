# Mail — «Поручения»: от постановки до отчёта (design, решения приняты)

Архитектура фичи «поручение на основе письма» с несколькими ответственными,
перепиской, встречами/селекторами, предложениями с голосованием и финальным
docx-отчётом. Постоянные и цикличные поручения, оповещение участников.

## 0. Принятые решения (зафиксированы Олегом)

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Транспорт | **Только почта** (Exchange EWS/EAS + IMAP). Других ресурсов нет — выделенный координатор/сервер исключён полностью, не только на MVP. |
| 2 | Участники без нашего клиента | Получают **человекочитаемое письмо** + приглашение на совещание в календарь (стандартный `.ics`/meeting request) — как обычно. Машинная часть для них не имеет значения. |
| 3 | Кворум решений | **Большинство голосов** по умолчанию; **владелец может принять решение единолично** в любой момент (override, а не отдельный режим). |
| 4 | Хранение / ИБ | Everything rides **обычную адресованную почту** — ничего сверх того, что ИБ уже проверяет. Без нового сервера, без общей папки/shared mailbox, без скрытых каналов. |
| 5 | Формат отчёта | **.docx** — переиспользуем существующий Node.js/docx-пайплайн (как в регламентах). |

Эти решения меняют дизайн относительно первой версии: убран вариант с
on-prem координатором (был «фаза 3») — его просто не будет, ресурсов для
сервиса нет. Вся система обязана работать **исключительно поверх обычных
писем**, которые видит и архивирует та же инфраструктура, что и остальную
почту организации.

## 1. Модель транспорта: событие = письмо

Задача (далее — «поручение») привязана к треду. Каждое действие — назначение,
предложение, голос, решение, смена статуса — рассылается **всем активным
участникам** как обычное адресованное письмо (To/Cc, без BCC-трюков и без
скрытых списков рассылки). Клиент каждого участника сворачивает историю писем
своего же почтового ящика в текущее состояние поручения — общего хранилища
нет, у каждого участника оно своё, восстановленное из его собственной почты.

### Почему это проходит ИБ (решение п.4)
- **Ничего нового с точки зрения инфраструктуры.** Нет нового сервера, порта,
  открытого извне сервиса, общей папки Exchange, повышенных прав. Только
  обычная отправка/приём писем через уже действующие Exchange/IMAP-каналы.
- **Полная прозрачность.** Машинная часть письма — не скрытое вложение, а
  промаркированная inline JSON-часть (`assignment-event.json`,
  `Content-Disposition: inline`) плюс человекочитаемое резюме в основном
  тексте. Ничего не спрятано от почтовых шлюзов, DLP, архивирования — всё
  видно так же, как в обычном письме.
- **Тот же аудит-периметр.** Раз это обычная почта, на неё автоматически
  распространяются уже утверждённые политики хранения/архивирования писем
  ОПО — не нужно отдельного согласования нового хранилища данных.
- **Целостность через существующий S/MIME.** Событие (особенно `vote` и
  `decision`) подписывается уже имеющимся у нас механизмом S/MIME — голос
  нельзя подделать/подменить, есть неотказуемость.

### Идемпотентность и порядок
- Стабильный `X-App-Task-Id` на все письма поручения (плюс корректные
  `References`/`In-Reply-To` — тред склеивается и в обычных почтовых клиентах).
- Каждое событие — `X-App-Event-Id` (UUID); дубликаты игнорируются локально.
- Порядок — по `createdAt` события; конфликтующие решения разруливаются
  правилом из §3.
- **Отстающий участник.** Если кто-то присоединился позже или пропустил
  письма (не в сети/фильтр), владелец жмёт «Обновить участника» — уходит
  одно письмо-снапшот текущего состояния (не пересылка всей истории).

Заголовки и коды формализованы в `lib/services/assignments/assignment_constants.dart`
(создан) — единая точка правды для будущего кодека и UI.

## 2. Доменная модель — реализовано в БД

Таблицы уже добавлены в `lib/data/database/app_database.dart` (schemaVersion
5 → 6, миграция `if (from < 6)` дописана, индексы созданы). Имя `Tasks` было
занято под PIM-задачу Exchange (один аккаунт/исполнитель) — поэтому новая
подсистема называется **`Assignments`** («Поручения»), без коллизии по смыслу.

```
Assignments             — карточка поручения (kind/status/owner/dueAt/recurrence…)
AssignmentParticipants  — участники и роли (owner/responsible/participant/observer)
AssignmentEvents        — журнал событий (источник истины, event sourcing)
AssignmentProposals     — предложения (проекция над событиями)
AssignmentVotes         — голоса участников (upsert, последний побеждает)
AssignmentMeetings      — встречи/селекторы/митинги/звонки, связь с CalendarEvents
AssignmentReports       — итоговый отчёт + путь к сгенерированному .docx
```

Полные определения колонок — в самом файле `app_database.dart`, они
прокомментированы по-русски рядом с каждым полем.

## 3. Жизненный цикл и логика решений

```
draft ──(разослать участникам)──▶ open ──▶ in_progress ──▶ review ──▶ done ──▶ closed
  └──────────────────────────── cancelled (владельцем, из любого статуса) ───────────┘
```

### Поток «предложение → голоса → решение» (решение п.3, формализовано)
1. Ответственный создаёт **proposal** (текст + вложения) → событие `proposal`.
2. Участники голосуют **support/reject/abstain** (+ комментарий) → событие `vote`
   (голос можно менять — новый `vote` от того же автора перекрывает предыдущий).
3. Подсчёт (`VoteTally` в assignment_constants.dart): «за» строго больше
   «против» (abstain не входит в знаменатель).
   - **Если `autoDecideEnabled=true`** (по умолчанию) и все ожидаемые
     участники ответили → клиент владельца **автоматически** формирует
     событие `decision` (`method=majority`). Это подсказка/автоматизация, а
     не отдельная роль — как и договаривались, «решает большинство».
   - **Ничья** → авто-решения нет, ждём владельца.
   - **Владелец в любой момент** (даже до того как все проголосовали, даже
     переопределяя уже принятое большинством решение) может зафиксировать
     `decision` с `method=owner_override` — это финально и перекрывает любой
     более ранний `decision` по этому предложению.
4. `accepted`-предложения уходят «в реализацию»; статус реализации
   отслеживается отдельным полем/событием (`checkpoint`/`report`), чтобы в
   финальный отчёт попало «реализовано», а не только «принято».

## 4. Типы поручений

- **Разовое (once).** Обычный цикл до `closed`.
- **Постоянное (permanent).** Без `dueAt`; вместо завершения — периодические
  чекпоинты-ревью (`nextCheckpointAt`, событие `checkpoint`) с мини-отчётом на
  каждый чекпоинт. Живёт, пока владелец не закроет вручную.
- **Цикличное (cyclic).** Запись с `isTemplate=true` + `recurrenceRule` (rrule —
  переиспользуем формат календаря). Планировщик (`background_service`, там же,
  где сейчас VIP/напоминания) порождает **инстанс** — новую строку
  `Assignments` с `parentAssignmentId` на шаблон; у каждого инстанса свой
  журнал событий и свой отчёт; участники/описание наследуются, можно
  переопределить перед рассылкой.

## 5. Встречи / селекторы / митинги

Из поручения создаётся встреча → уже существующий путь `createEvent`
(фасад `mail_engine_service`, EAS→движок/EWS→ews_service) с участниками
поручения как attendees. Связь `AssignmentMeetings.calendarEventId ↔ event`.
Подтип (`selector/meeting/standup/call`) — своё поле `dialIn`/`link`.

**Для участников без нашего клиента (решение п.2)** — никакой особой логики
не требуется: приглашение на встречу они получают штатно через календарь
(iCalendar/meeting request), как и всегда; в письмах по треду видят обычный
человекочитаемый текст. Наша машинная часть им просто не интересна и ничего
не ломает — она inline и не мешает чтению письма в любом клиенте.

Итоги встречи (протокол/решения) вносятся в `minutes` и могут породить новые
`proposal`/`decision` события — то есть встреча не выпадает из общей ленты.

---

## 6. Оповещения участников

Триггеры: назначение роли, новое предложение, запрос голоса, назначена
встреча, смена статуса, зафиксировано решение, отчёт готов, приближается
срок/чекпоинт, порождён цикличный инстанс.

Канал доставки для наших пользователей — то же письмо (оно и есть носитель
события) **плюс** локальное push/in-app уведомление поверх уже имеющегося
notifications-слоя (тихие часы, важность по роли — переиспользуем
существующие настройки VIP-оповещений). Для внешних участников — только
письмо (решение п.2), для встреч — плюс стандартное приглашение календаря.

## 7. Формат письма-события (конверт)

- **Заголовки:** `X-App-Task-Id`, `X-App-Event-Id`,
  `X-App-Event-Type`, `X-App-Event-Version` + обычные
  `References`/`In-Reply-To`/`Message-ID` для склейки треда в любом клиенте.
- **Тема:** `[Поручение] <title> — <человекочитаемая суть события>` — понятна
  и без нашего приложения.
- **Тело:** человекочитаемое резюме (RU, основной текст) + промаркированная
  inline JSON-часть `assignment-event.json` (см. §1 про ИБ-прозрачность).
- **Подпись:** S/MIME поверх всего письма (существующий механизм).
- Все константы и enum-коды — в `lib/services/assignments/assignment_constants.dart`.

## 8. UI (к реализации)

- **«Создать поручение из письма»** — действие в карточке письма: заголовок/
  описание из письма, вложения тянутся, участники — из GAL/контактов с
  ролями, тип (разовое/постоянное/цикличное) + повторение, срок,
  `autoDecideEnabled`.
- **Экран поручения:** шапка (статус/тип/срок), участники с ролями, единая
  **лента** (переписка/встречи/предложения/голоса/решения), карточки
  предложений с кнопками «поддержать/отклонить» и live-счётчиком, кнопка
  «назначить встречу», кнопка «собрать отчёт».
- **Список/доска:** канбан по статусам; фильтры (мои / где я ответственный /
  просроченные / цикличные / постоянные).
- **Отчёт:** авто-сборка секций из проекции (рассматривали = все proposals;
  приняли/отклонили = decisions; реализовали = accepted+done), правка текста,
  экспорт в .docx через существующий doc-пайплайн (решение п.5).

## 9. Этапность

**Готово (реализовано в коде):**
- Схема БД: 7 таблиц `Assignment*`, миграция v5→v6, индексы —
  `lib/data/database/app_database.dart`.
- Wire-контракт: `lib/services/assignments/assignment_constants.dart`.
  Уточнение по ходу реализации: у `MailTransport.send()` нет кастомных
  SMTP-заголовков и MIME-вложений на уровне абстракции (и трогать этот не
  раз чинившийся код ради этого не стоило) — машинная часть события теперь
  видимый текстовый блок внутри `bodyHtml` между простыми маркерами, а не
  отдельная MIME-часть. Для ИБ это даже лучше: совсем ничего не спрятано.
- Кодек письма-события (сборка/разбор) —
  `lib/services/assignments/assignment_event_codec.dart`.
- Проекция — событийный редьюсер, применяет события к таблицам, идемпотентно
  (по eventId), возвращает сигнал авто-решения —
  `lib/services/assignments/assignment_projection_service.dart`.
- Оркестрация: создание поручения из письма, предложения, голосование с
  авто-фиксацией решения большинством (только с клиента владельца — не
  клиента каждого проголосовавшего, чтобы не было дублей), owner-override,
  смена статуса, рассылка всем участникам (To — голосующие, Cc — observer) —
  `lib/services/assignments/assignment_service.dart`.
- Хук во входящую синхронизацию: после сохранения новых писем (все три пути —
  движок/EAS, EWS, IMAP) письма сканируются на события поручений и
  применяются к проекции — `lib/services/sync/sync_service.dart`
  (`_scanForAssignmentEvents`, в try/catch — не может сломать обычный синк).

**Далее — фаза 1 (осталось для MVP):**
- UI: «Создать поручение из письма» в карточке письма, экран поручения с
  лентой, карточки предложений с кнопками голосования, список/доска.
- Оповещения (in-app поверх существующего notifications-слоя).
- Разовые поручения — уже полностью работают на уровне сервиса; не хватает
  только UI, чтобы ими пользоваться руками.

**Фаза 2:**
- Встречи/селекторы (интеграция календаря через уже существующий
  `mail_engine_service.createEvent`), планировщик цикличных/постоянных
  поручений (спавн инстансов, чекпоинты), экспорт отчёта в .docx.

**Фаза 3:**
- Канбан-доска, аналитика по поручениям, донастройка кворума на уровне
  поручения (таймаут авто-решения и т.п.).
- On-prem координатор — **исключён окончательно** (решение п.1): весь
  real-time (если понадобится) придётся имитировать частым локальным
  пере-сканированием почты, а не выделенным сервисом.

## 10. Мелкие открытые вопросы (не блокируют старт)

1. Таймаут авто-решения, если часть участников не отвечает (напоминание →
   потом решение переходит к владельцу вручную, без авто-большинства)?
2. Участников-observer учитывать в знаменателе голосования или нет
   (текущее предположение — нет, голосуют owner+responsible+participant)?
3. Где физически рендерить `.docx`-отчёт при отсутствии сети — сразу при
   «собрать отчёт» локально (у нас уже есть офлайн Node/docx-пайплайн) —
   видимо да, подтвердить.
