# OAuth-прокси ogneliss.ru — чистая переустановка (октябрь 2026)

Что было: Яндекс отвечал `invalid_client` — в коде не было `authStyle: 'basic'`
(исправлено в server.js). Прокси перевели на systemd, и вслед за этим
понадобились: путь в юните, права, `npm install`, `HOST=0.0.0.0`, iptables,
адрес шлюза Docker `172.24.0.1` в NPM. Главная причина «исправления не
действуют» — старый контейнер `oauth-proxy` со старым кодом, который не
пересобрали.

Gmail после переезда: `/token` → 401. Ключ приложения верный (иначе не
прошёл бы и вход Яндекса — `/exchange` требует тот же ключ), `.env` тот же
(`/opt/mailserver/oauth-proxy/.env` — его же использует docker-режим скрипта),
значит, 401 вернул сам Google. Самое вероятное — ручная правка `tokenRequest`
убирает `client_id`/`client_secret` из тела для ВСЕХ провайдеров, а не только
для `basic`. Ниже — возврат к коду из репозитория.

## Одной командой: reinstall-oauth-proxy.sh (рекомендуется)

Находит ВСЕ прежние установки (Docker-контейнер, службы systemd `oauth-proxy`
и `ogneliss-oauth-proxy`, `.env` в /opt/mailserver, /opt/oauth-proxy,
/etc/ogneliss-oauth-proxy), сохраняет их в `/root/oauth-proxy-backup-<дата>`,
удаляет (вместе с правилами iptables для 8787) и ставит заново в Docker с
ПРЕЖНИМИ секретами — входы пользователей сохраняются, приложение не нужно
пересобирать. Если найдены разные наборы секретов, скрипт остановится и
попросит указать нужный (`--env ФАЙЛ`).

```bash
cd /путь/к/архиву/server/oauth-proxy
sudo bash reinstall-oauth-proxy.sh --dry-run    # посмотреть план, ничего не меняя
sudo bash reinstall-oauth-proxy.sh              # выполнить
```

В конце скрипт попросит поменять адрес в NPM (Forward Hostname `oauth-proxy`,
порт 8787) и проверит прокси снаружи.

## Вручную: обратно в Docker, под управлением install-oauth-proxy.sh

Нет жёстко прописанного адреса шлюза, порт 8787 не открыт наружу, iptables не
нужен, обновление — одной командой с пересборкой образа.

```bash
# 0. Резервная копия секретов (ENC_SECRET, PROXY_API_KEY, STATE_SECRET,
#    *_CLIENT_ID/SECRET). Без них пользователи теряют вход.
sudo cp -a /opt/mailserver/oauth-proxy/.env /root/oauth-proxy.env.$(date +%F)

# 1. Остановить systemd-вариант
sudo systemctl disable --now oauth-proxy
sudo rm -f /etc/systemd/system/oauth-proxy.service && sudo systemctl daemon-reload
# правила iptables для 8787 больше не нужны
sudo iptables -D INPUT -p tcp --dport 8787 -s 172.16.0.0/12 -j ACCEPT
sudo iptables -D INPUT -p tcp --dport 8787 -j DROP
sudo netfilter-persistent save
# HOST=0.0.0.0 из .env можно убрать: в контейнере его задаёт compose

# 2. Код из архива (каталог server/oauth-proxy) и пересборка контейнера.
#    update не трогает секреты и делает «up -d --build».
cd /путь/к/архиву/server/oauth-proxy
sudo bash install-oauth-proxy.sh update --mode docker

# 3. Только ПОСЛЕ запуска контейнера — NPM (иначе nginx -t не пройдёт, как раньше):
#    Hosts → Proxy Hosts → ogneliss.ru → Custom Locations → /oauth
#    Scheme http, Forward Hostname: oauth-proxy, Port: 8787 → Save

# 4. Проверка
sudo bash install-oauth-proxy.sh check
curl -s https://www.ogneliss.ru/oauth/healthz
```

## Вариант Б: оставить systemd

Работает, но держится на адресе шлюза `172.24.0.1` (сменится при пересоздании
сети Docker) и открытом на 0.0.0.0 порту. Если оставляете — замените только код:

```bash
sudo cp server.js package.json /opt/mailserver/oauth-proxy/
sudo systemctl restart oauth-proxy
```

`docker-compose.oauth.yml` в этом варианте не запускать (переименовать в
`.disabled`), контейнер `oauth-proxy` не возвращать.

## Что проверить после любого варианта

`/healthz` теперь показывает настройку без секретов:

```json
"config": { "google": {"clientId": true, "clientSecret": true, "auth": "body"},
            "yandex": {"clientId": true, "clientSecret": true, "auth": "basic"} },
"keys":   { "api": "97b2173c", "enc": "1bd8fd47" }
```

- `google.clientSecret: false` — в `.env` нет `GOOGLE_CLIENT_SECRET`.
- `keys.api` должен совпасть с «отпечатком ключа» в диагностике приложения
  (Настройки → Журнал → Диагностика). Не совпал — прокси и приложение
  собраны с разными `PROXY_API_KEY`.
- `keys.enc` должен остаться прежним после любых переездов — иначе ранее
  выданные входы не расшифруются, и все OAuth-ящики придётся входить заново.

Причина каждого отказа провайдера теперь пишется в журнал службы:

```bash
sudo docker logs -f oauth-proxy          # вариант А
sudo journalctl -u oauth-proxy -f        # вариант Б
# пример: oauth-proxy: google refresh_token → HTTP 401 invalid_client (...)
```

- `invalid_client` — неверные `GOOGLE_CLIENT_ID/SECRET` в `.env` (или они не
  уходят в запросе — см. начало).
- `invalid_grant` / `unauthorized_client` — вход отозван или выдан другому
  клиенту: в приложении «Войти снова» у ящика Gmail.

Приложение (с этой версии) тоже пишет причину: «OAuth proxy /token (blob)
HTTP 401: …».
