# Переписывание на нативный Android (Kotlin) — оценка

Ответ на вопрос: сколько времени займёт и нужно ли это, если Android станет
единственной платформой.

---

## 1. Что придётся переписать

Замеры по текущему коду:

| Слой | Строк | Переносимость |
|---|---:|---|
| UI (`lib/features`) | 26 900 | **0%** — Compose пишется с нуля, 68 экранов |
| Сервисы (`lib/services`) | 25 074 | ~40% — алгоритмы переносятся по смыслу, код заново |
| Ядро транспорта (`packages/`) | 3 660 | ~50% — логика протоколов ценна, синтаксис другой |
| Виджеты, core, data | 6 964 | ~20% |
| Локализация | 1 714 | ~90% — строки переносятся в `strings.xml` почти как есть |
| **Итого** | **~65 000** | |

«Переносимость» здесь — доля, которую можно перенести **по логике** (алгоритм
понятен, решения приняты, крайние случаи известны). Печатать код всё равно
придётся заново: Dart → Kotlin автоматически не превращается.

### Что менять целиком
· **Riverpod → ViewModel + Flow/StateFlow.** Вся логика состояния приложения.
· **Drift → Room.** Схема (14 версий) переносится, но DAO и запросы заново;
  миграции придётся написать так, чтобы существующие базы открылись.
· **go_router → Navigation Component.**
· **flutter_html / html_editor_enhanced → WebView + собственная обвязка.**
  Готового аналога редактора с панелью инструментов в Android нет.
· **pdf (Dart) → iText / PdfDocument**, включая кириллические шрифты.
· **74 пакета** из pubspec — для части аналоги очевидны, для части нет.

### Что реально ценно и переносится
· **WBXML-кодек ActiveSync** (3 987 строк) — самая трудоёмкая часть, писалась
  по спецификации и отлаживалась. Логику можно перенести один в один.
· **Сборка и разбор EWS SOAP** (3 558 строк), включая адресацию общих ящиков.
· **Правила и регулярки**: извлечение сроков, распознавание цитат, определение
  перевозчика, антифишинг, DLP. Тут перенос почти механический.
· **Принятые решения**: что делать при обрыве, как вести очередь, когда
  предупреждать пользователя. Это дороже кода — оно уже проверено обсуждением.

## 2. Сроки

Оценка для **одного опытного Android-разработчика**, полный рабочий день:

| Этап | Срок |
|---|---|
| Каркас, навигация, БД (Room + миграции) | 3–4 недели |
| Транспорты: EAS, EWS, IMAP/SMTP | 2–2,5 месяца |
| Синхронизация, очередь, офлайн | 1–1,5 месяца |
| UI: 68 экранов | 3–4 месяца |
| Редактор писем, просмотр HTML, PDF | 3–4 недели |
| Уведомления, безопасность, биометрия | 3 недели |
| Отладка, тестирование на боевом Exchange | 1,5–2 месяца |
| **Итого** | **9–14 месяцев** |

Оценка без «эффекта второй системы»: считаем, что архитектура повторяется,
а не изобретается заново. С экспериментами срок вырастет.

Двое разработчиков сократят срок примерно до 6–8 месяцев, но не вдвое:
транспорты и синхронизация плохо параллелятся.

---

## 3. Что даст переход

**Реальные выгоды**
· **Размер приложения**: ~10–15 МБ против нынешних 25–30 МБ.
· **Запуск**: на 200–400 мс быстрее (нет инициализации Flutter engine).
· **Виджеты рабочего стола и Wear OS** — пишутся напрямую, без канала связи.
· **Системная интеграция**: Direct Share, автозаполнение, работа с контактами
  и календарём ОС — без прослойки.
· **Один язык** для приложения и нативных плагинов (сейчас Dart + 5 файлов
  Kotlin).

**Выгоды сомнительные**
· *Производительность интерфейса.* Для почтового клиента Flutter достаточно
  быстр; узкое место — сеть и разбор писем, а не отрисовка.
· *Стабильность.* Текущие проблемы (если появятся) — в логике, а не в Flutter;
  они переедут вместе с логикой.

---

## 4. Что будет потеряно

· **Windows-версия.** В проекте есть поддержка десктопа: трей, окно, адаптивная
  вёрстка под большой экран, документ по сборке под Windows. При переходе на
  Kotlin она исчезает. Если ею пользуются — это решающий аргумент против.
· **9–14 месяцев развития.** Всё это время новые функции не появляются.
· **Отлаженный код.** Сейчас закрыты десятки неочевидных случаев: обрыв связи
  при отправке, дубликаты писем, вложения в пересылке, цитаты русского
  Outlook, права на общие ящики. При переписывании часть всплывёт заново.
· **Возможность вернуться на iOS**, если когда-нибудь понадобится.

---

## 5. Вывод

**Переписывание не оправдано, если нет конкретной проблемы, которую Flutter
создаёт.** Замена работающей системы ради архитектурной чистоты обходится в
год работы и почти гарантированно даёт новые ошибки в тех местах, где старые
уже найдены.

**Когда переписывание оправдано:**
1. Windows-версия не нужна и не планируется.
2. Нужна глубокая системная интеграция — виджеты, Wear OS, Direct Share — и
   именно она составляет ценность продукта.
3. Команда сопровождения знает Kotlin и не знает Dart. Это довод серьёзнее
   технических: поддерживать код должен тот, кто его понимает.
4. Появились проблемы, которые упираются в сам Flutter, а не в логику.

**Что сделать вместо переписывания, если нужна нативность:**
· **Виджеты рабочего стола и Wear OS** — пишутся на Kotlin и общаются с
  приложением через `MethodChannel`. Это дни работы, а не месяцы; в проекте уже
  есть 5 таких плагинов (контакты, календарь, распознавание речи, фоновая
  синхронизация).
· **Тяжёлые операции** (разбор больших писем, шифрование) — выносятся в
  нативный модуль точечно.
· **Системные интеграции** — тем же способом.

Так нативные возможности появляются там, где они действительно нужны, без
остановки развития на год.

**Промежуточный вариант**, если решение о Kotlin принято: не переписывать
сразу, а выносить в нативный код по одному блоку, начиная с транспортов, и
держать две части рядом. Дольше по календарю, но приложение всё время
работает, а не лежит в переписывании.
