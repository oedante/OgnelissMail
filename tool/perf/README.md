# Замеры скорости на эмуляторе (tool/perf)

1.9.x, просьба владельца 31.10.2026. Задача `emulator` в
`.github/workflows/ci.yml` запускает `integration_test/emulator_test.dart`
на эмуляторе Android (API 34, x86_64, Pixel 6). Замеры —
`integration_test/perf_test.dart`:

| Замер | Что меряется |
|---|---|
| `mail_open_first_ms` | первое открытие письма в процессе: от «нажатия» (переход на экран письма) до показа текста; движок браузера ещё не загружен |
| `mail_open_ms` | повторное открытие (медиана трёх) |
| `mail_open_spare_ms` | открытие с запасным окном (MailWebViewPool), медиана трёх |
| `compose_first_ms` | первое «Новое сообщение» до готового редактора (файлы редактора читаются) |
| `compose_ms` | повторное (медиана трёх) |
| `compose_spare_ms` | с запасным окном редактора (MailEditorPool), медиана трёх |
| `app_first_frame_ms` | запуск без аккаунтов: от `main()` до первого кадра заставки |
| `app_first_screen_ms` | до первого экрана после заставки (заставка держится не меньше 1,8 с) |
| `scroll_sync_build_ms` | прокрутка ленты во время синхронизации (2.6.8): сборка кадра, 90-й процентиль |
| `scroll_sync_worst_frame_ms` | там же: худший кадр целиком (от сигнала кадра до конца отрисовки) |

У открытия письма в `perf-results.json` есть и этапы `OpenTrace` (окно,
создано, кадр, загрузка, текст) — по ним видно, что замедлилось.

Прокрутка во время синхронизации: лента папки на 400 писем прямо из базы
(как в приложении — поток запроса, модели строк, `EmailListTile`), каждые
300 мс приходит пачка из 20 писем (тексты разбираются в главном потоке) и
меняются отметки прочитанного у 40; восемь быстрых пролистываний вверх и
вниз. В `perf-results.json` у `scroll_sync_build_ms` — сводка кадров
(`frames`: число кадров, сколько собирались дольше 16 мс —
`missed_frame_build_budget_count`, среднее и худшее время сборки, кадров
дольше 34 мс целиком). База для `scroll_sync_*` — начальная, с запасом (на
Linux в отладочной сборке: 90-й процентиль сборки 53 мс, худший кадр
167 мс); обновить после первого прогона на эмуляторе.

## Метки производительности (PerfMark)

2.6.8, план «Ж». Крупные участки работы отмечены в Timeline
(`lib/core/logging/perf_mark.dart`):

| Метка | Где |
|---|---|
| `синхронизация: <этап>` | каждый этап синхронизации ящика (список папок, папка, календарь и контакты…) |
| `IMAP: сверка удалённых`, `IMAP: сверка писем` | проверка, какие письма удалены на сервере и каких нет на устройстве (главный поток) |
| `открытие письма` | от нажатия до показа текста, с отметками этапов `OpenTrace` |
| `письмо: разбор HTML` | разбор и очистка HTML письма перед показом (главный поток) |
| `лента: письма из базы`, `лента: группы по дням` | строки ленты из базы и группы по дням при каждом её обновлении (главный поток) |

Где видно:

- **DevTools** — сборка profile (`flutter run --profile`), вкладка
  «Performance»: метки лежат на шкале рядом с кадрами. В выпуске Timeline
  выключен, метка стоит два чтения часов.
- **Журнал приложения** — у медленного кадра (дольше 250 мс) пишется, что
  в это время шло: «Медленный кадр: 812 мс (ожидание 790, …) — главный
  поток: письмо: разбор HTML 420 мс; шло: синхронизация: папка Входящие».
  Без отладчика: так видно по журналу пользователя, что держало интерфейс.

Новую метку ставить на участок, который может занять больше нескольких
миллисекунд: `PerfMark.sync('имя', () => …)` — для работы в главном потоке,
`PerfMark.run('имя', () async => …)` — для участка на несколько кадров. Имя —
без адресов и текста писем (журнал уходит в поддержку).

Сборка отладочная (`flutter test` на устройстве другой не делает), графика
программная, процессоры общие: числа больше, чем на телефоне, и шумят.
Поэтому ошибка — только если замер **больше базы вдвое**; медленнее базы,
но меньше чем вдвое, — предупреждение в сводке.

## Запуск

- GitHub: Actions → CI/CD → Run workflow → отметка «emulator» (и на каждой
  метке `v*`). Результат — таблица в сводке сборки и `perf-results.json` в
  Artifacts (`emulator-<коммит>`).
- Локально (эмулятор или телефон подключён, `adb devices` его видит):
  `bash tool/dev/emulator_tests.sh [устройство]`, затем
  `python3 tool/perf/perf_check.py extract emulator-machine.jsonl emulator-logcat.txt -o perf-results.json`
  и `python3 tool/perf/perf_check.py compare perf-results.json`.

## Обновить базу

База — `tool/perf/baseline.json`. Начальные значения взяты с запасом, до
первого прогона на GitHub. Обновлять после первого удачного прогона и
когда скорость сознательно изменилась (ускорили — база ниже, иначе
замедление снова пройдёт незамеченным; осознанно замедлили — выше):

1. Скачать `perf-results.json` из Artifacts удачной сборки `emulator`.
2. `python3 tool/perf/perf_check.py baseline perf-results.json` — база =
   замеры × 1,5, вверх до 50 мс (`--headroom`, `--step`).
3. Проверить разницу (`git diff tool/perf/baseline.json`) и записать её
   отдельным коммитом с причиной.

Один прогон шумит (машины GitHub разные: первое «Новое сообщение» бывало
и 2,1 с, и 6,4 с), поэтому лучше брать медиану нескольких удачных прогонов:
собрать её в один `perf-results.json` (`{"metrics": {…}}`) и подать в
шаг 2 — так сделана база 07.11.2026.

Новый замер в тесте без строки в базе отмечается «🆕» и ошибкой не
считается; строка базы без замера — предупреждение.
